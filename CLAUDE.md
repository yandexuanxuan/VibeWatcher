# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

VibeWatcher monitors Claude Code CLI execution and broadcasts state changes over WebSocket to a VSCode extension. Four packages managed via npm workspaces — shared types live in `vibewatcher-shared`.

**Current status: v1.0 is complete.** All MVP and enhancement features are implemented.

## Build & Test Commands

```bash
# Node 20 recommended (Jest requires Node 14+)
export NVM_DIR="$HOME/.nvm" && . "$NVM_DIR/nvm.sh" && nvm use 20

# Build all packages (from repo root)
npm run build

# Run tests
npm test

# Clean
npm run clean

# Individual packages
cd vibewatcher-cli && npm run build && npm test
cd vibewatcher-server && npm run build && npm test
cd vibewatcher-vscode && npm run compile

# One-click install
bash install.sh

# Daemon management
vibe-daemon start              # Start server in background
vibe-daemon stop               # Stop server
vibe-daemon status             # Check server status
vibe-daemon log                # View server logs

# VSCode extension packaging
cd vibewatcher-vscode && vsce package
code --install-extension vibewatcher-0.4.0.vsix --force
```

## Architecture

Three-layer data flow:

```
CLI Wrapper (vibewatcher-cli)
  → spawns child process, captures stdout/stderr
  → regex pattern matcher detects "waiting for input" prompts
  → emits WebSocket events to server
  ← receives STOP_TASK messages to kill child process

Event Server (vibewatcher-server)
  → WebSocket server on port 9234 (configurable via VIBEWATCH_PORT env var)
  → TaskManager manages task lifecycle, StateStore holds in-memory state
  → broadcasts events to all connected clients
  → forwards STOP_TASK broadcast to CLI clients
  → StallDetector monitors task output for stalls
  → AIInterpreter provides LLM-based task interpretation

VSCode Extension (vibewatcher-vscode)
  → connects to server on activation (onStartupFinished)
  → status bar indicator, TreeView task list, desktop notifications
  → sends STOP_TASK via WebSocket when user clicks "Stop Task"
```

**Task state machine:** `INIT → RUNNING ⇄ WAITING_INPUT → COMPLETED | ERROR`

**WebSocket message types:**
- `TASK_CREATED`, `TASK_STATUS`, `TASK_OUTPUT`, `TASK_EXIT` — core lifecycle
- `LIST_TASKS`/`TASKS_LIST` — task list refresh
- `STOP_TASK` — kill task signal
- `TASK_SUMMARY` — execution summary (auto-generated by CLI)
- `TASK_PREDICTION` — duration prediction based on history
- `TASK_STALL` — stall detection alert
- `INTERPRET_TASK`/`TASK_INTERPRETATION` — AI-powered task interpretation

**Data directories:**
- `~/.vibewatch/summaries/{taskId}.md` — task execution summaries (generated by CLI)
- `~/.vibewatch/history.json` — task history for duration prediction (written by server)
- `~/.vibewatch/config.json` — user config (notifications, AI, stall detection, etc.)
- `~/.vibewatch/run/vibewatcher.pid` — daemon PID file

## Key Design Decisions

- **Daemon mode**: Server runs in background via `vibe-daemon` script, with PID file at `~/.vibewatch/run/vibewatcher.pid`
- **Auto-start**: CLI, VSCode extension, and `vibe` wrapper all auto-start daemon if not running
- **Graceful degradation**: CLI continues in standalone mode if server unavailable
- Server auto-increments port on conflict (9234–9237 range, 3 retries)
- Prompt detection uses fixed regex patterns (no LLM) — see `vibewatcher-cli/src/matcher.ts`
- CLI receives incoming messages via `WebSocketClient.onMessage()` for STOP_TASK support
- VSCode extension auto-starts daemon on activation if not already running
- All packages target ES2020, commonjs module, TypeScript strict mode
- .vscodeignore excludes src/, node_modules/, tsconfig.json from .vsix packaging

## Important Notes

- Shared types are in `vibewatcher-shared/src/types.ts` — all packages import from `vibewatcher-shared`
- `vibewatcher-server/` had an independent `.git` directory — it has been removed, this repo is the single source of truth
- Root `package.json` provides workspace-level build/test/clean scripts
- Security: taskId is validated with UUID regex before use in file paths
- Security: WebSocket message structure is validated before processing
- Security: notification tokens are never logged in error messages
